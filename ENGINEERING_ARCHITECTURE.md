# ZILTON LIFE CARE PRIVATE LIMITED

## Engineering & Architecture Document

**Version:** 1.0 --- Working baseline\
**Status:** Draft for team validation\
**Purpose:** Shared technical source of truth for both developers and
their AI coding assistants.

------------------------------------------------------------------------

## 1. Engineering principles

1.  Build the agreed V1 corporate website; do not introduce unrequested
    product features.
2.  Keep content separate from presentation.
3.  Build reusable components with clear, stable interfaces.
4.  Prefer simple solutions over unnecessary abstractions.
5.  Keep the application statically renderable and SEO-friendly.
6.  Never place secrets or private credentials in browser code.
7.  Do not fabricate business, manufacturing, certification or product
    information.
8.  Make small, reviewable pull requests.
9.  Run checks before requesting review.
10. Update documentation when an approved architecture decision changes.

## 3. Application architecture

Use a small, modular frontend architecture:

-   Route modules compose page-level sections.
-   Shared UI components live separately from page-specific sections.
-   Company and product content live in typed data modules.
-   Form schema and submission service are separate from the visual
    form.
-   Design tokens are centralized.
-   No global state library is needed for V1 unless a concrete use case
    emerges.

### 3.1 Suggested route map

Use React Router's framework route configuration and route module
conventions. The exact filenames should follow the scaffold generated by

## 5. Component contracts

Agree these interfaces before both developers build page sections.
Interfaces can evolve through a reviewed PR.

### 5.1 Button

Suggested API:

``` tsx
type ButtonProps = {
  children: React.ReactNode;
  to?: string;
  href?: string;
  type?: "button" | "submit" | "reset";
  variant?: "primary" | "secondary" | "outline" | "text";
  size?: "sm" | "md" | "lg";
  className?: string;
  disabled?: boolean;
};
```

Use a router link for internal navigation and a normal anchor for
external URLs. Do not nest interactive elements.

### 5.2 Container

``` tsx
type ContainerProps = {
  children: React.ReactNode;
  className?: string;
};
```

Provides the consistent max-width and horizontal page padding.

### 5.3 SectionHeading

``` tsx
type SectionHeadingProps = {
  eyebrow?: string;
  title: string;
  description?: string;
  align?: "left" | "center";
  className?: string;
};
```

### 5.4 Product data model

``` tsx
export type ProductCategory =
  | "critical-care-injection"
  | "nutrition-iv"
  | "nutrition-sachet";

export type Product = {
  id: string;
  name: string;
  category: ProductCategory;
  image: string;
  shortDescription: string;
  published: boolean;
};
```

Only populate records with client-approved product data. Do not invent
sample products that could accidentally ship. If placeholder content is
needed for layout, clearly label it as development-only and prevent
publication.

### 5.5 Navigation

Keep navigation items in one data module. Use route paths as constants
where practical to avoid typos.

## 6. Design system implementation

Create shared CSS/Tailwind tokens for the agreed initial palette:

-   Primary emerald: `#087B59`
-   Primary hover: `#066447`
-   White: `#FFFFFF`
-   Soft mint: `#E8F4EE`
-   Deep forest: `#173B30`
-   Body text: `#46534C`
-   Border: `#DCE8E0`

Typography: - Manrope for headings. - Inter for body text.

Implementation requirements: - Verify colour contrast; do not assume the
palette automatically passes WCAG. - Establish spacing, container
widths, border radii, shadows and focus-ring rules. - Avoid arbitrary
one-off values when a shared token exists. - Use responsive typography
and layouts. - Respect `prefers-reduced-motion`.

## 7. Contact form architecture

The form should be isolated from page presentation.

Suggested files: - `app/schemas/contact.schema.ts` -
`app/services/contact.service.ts` - Contact form component under
`components/sections/contact/`

Schema should validate: - Full name (required). - Organization
(optional). - Email (required, valid format). - Phone (required; allow
appropriate international formats). - Enquiry type (required enum). -
Message (required, reasonable maximum length). - Consent only where
legally/operationally appropriate and client-approved.

Service contract can initially be:

``` tsx
export type ContactPayload = {
  fullName: string;
  organization?: string;
  email: string;
  phone: string;
  enquiryType: "general" | "business-partnership" | "product-related";
  message: string;
};

export async function submitContactForm(
  payload: ContactPayload
): Promise<{ success: boolean; message?: string }> {
  // Implement only after the form provider/server endpoint is selected.
  throw new Error("Contact service is not configured yet.");
}
```

Do not leave the placeholder throwing error in a production release.
Select and test a real submission path before the form is considered
complete.

Provider decision is pending. Evaluate Formspree, Web3Forms, or a
serverless endpoint plus email provider based on: - Pricing and
submission limits. - Email delivery and reliability. - Spam controls and
rate limiting. - Data location, retention and privacy terms. - Required
secrets and deployment configuration. - Client's ability to own/manage
the account.

Never put SMTP credentials or private API keys in `VITE_*` variables or
client bundles. Treat Vite-exposed variables as public.

## 8. Static rendering and SEO

-   Configure React Router Framework Mode pre-rendering for all public
    routes.
-   Confirm the build generates usable HTML for each public route.
-   Test direct URL navigation and refresh on nested routes.
-   Ensure page titles and descriptions are unique.
-   Add Open Graph metadata.
-   Add sitemap and robots configuration.
-   Add canonical URLs after the final domain is known.
-   Use descriptive alt text; decorative images should have empty alt
    text.
-   Use structured data only for verified company details.
-   Check that production pages are indexable and not unintentionally
    `noindex`.
-   Do not rely on client-side rendering alone for important page
    content.

## 9. Images and assets

-   Store optimized, approved assets in `public/images/`.
-   Use descriptive, consistent filenames.
-   Prefer WebP/AVIF where browser support and build workflow allow,
    retaining suitable fallbacks.
-   Provide explicit dimensions/aspect ratios to reduce layout shift.
-   Lazy-load below-the-fold images; prioritize the hero image
    appropriately.
-   Do not use copyrighted competitor logos or copy competitor page
    designs.
-   Temporary stock images must be licensed and replaceable.
-   Product images must come from the client; do not generate fake
    packaging or imply that a mock product is real.

## 10. Git and collaboration workflow

Repository name proposal: `zilton-life-care-website`.

Branch model: - `main` is the stable integration branch. - Use
short-lived feature branches. - No direct pushes to `main`. - No
`develop` branch is required for a two-person team.

Examples: - `feature/design-system` - `feature/navbar-footer` -
`feature/homepage` - `feature/about` - `feature/products` -
`feature/quality` - `feature/contact` - `feature/seo-legal`

Pull request process: 1. Create an issue or agree a task. 2. Create a
feature branch from updated `main`. 3. Implement only the assigned
scope. 4. Run formatting, lint, typecheck and build checks. 5. Open a PR
with screenshots for UI changes and test notes. 6. Teammate reviews code
and tests. 7. Resolve comments and merge. 8. Pull the latest `main`
before starting the next dependent task.

Protect `main` with PR review and automated checks where repository
settings permit.

## 11. Quality gates

Before a PR is ready: - TypeScript has no new errors. - Lint/format
checks pass. - Production build passes. - No console errors
introduced. - Responsive layout checked at relevant widths. - Keyboard
interaction and focus checked. - Links and forms tested. - No secrets or
unapproved claims added. - No unrelated files modified. - Screenshots
attached for meaningful UI changes.

Before release: - Test every route directly and via navigation. - Test
form success and failure paths. - Test mobile menu. - Check image
loading and alt text. - Check 404 handling. - Check SEO metadata and
static HTML. - Run Lighthouse and accessibility checks. - Obtain client
content/compliance approval.

## 12. AI coding assistant operating rules

Both developers must give their AI assistant the same three project
documents and current repository context.

Every AI task should specify: - Assigned developer and role. - Exact
task and acceptance criteria. - Files allowed to create/modify. -
Existing components/contracts to reuse. - Dependencies and integration
points. - Commands/tests to run. - Explicit exclusions.

AI assistants must: 1. Read the project documents before proposing
implementation. 2. Inspect the current repository before editing. 3.
Avoid replacing working files or changing architecture without approval.
4. Never fabricate company/product/certification facts. 5. Never add
secrets, credentials or private tokens. 6. Avoid installing dependencies
without explaining why. 7. Keep changes scoped and explain each changed
file. 8. Run relevant checks and report actual results; never claim
tests passed if they were not run. 9. Flag missing client content rather
than inventing it. 10. Ask before making a change that affects another
developer's owned area or a shared component contract.
